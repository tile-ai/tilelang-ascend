# Expert v2：先搭好流水，再找到值得改的地方

这个示例计算完整的非因果 attention：先用 query 与 key 的点积得到分数，再用 softmax
把分数变成权重，最后对 value 加权求和。长序列的分数矩阵很大，不能全部留在片上，
所以实现按块计算，并逐步更新统计量和输出，不保存完整矩阵。

在昇腾上，矩阵乘法由 Cube 单元完成，softmax 和输出更新由 Vector 单元完成。
优化的目标不只是让某一步更快，还要让这两类计算与内存搬运尽量同时推进。
下面说明 [`kernel.py`](kernel.py) 为什么最终保留普通 FP32 归约和三个工作区槽。

## 1. 分块以后，还要让各道工序接得上

基本流程是：Cube 算一块分数，Vector 把分数转换成权重，Cube 用权重计算这一块的
输出贡献，Vector 再把它合入输出。在线 softmax 保存已处理块的最大值与指数和，
遇到新的最大值时重新缩放旧统计量和输出，最后得到对完整序列归一化的结果。

如果只准备一份交接工作区，一方使用数据时，另一方就不能覆盖它。因此工作区分成多个槽：
Vector 消费旧槽时，Cube 可以准备新槽。每个槽都要等使用方归还后才能复用，
否则流水虽然能继续跑，数据却可能已被下一块覆盖。

这条完整流水是后续实验的基础。更早版本的完整演变记录已不齐，本文不补写一条连续的
版本故事；重点保留能够解释当前选择的尝试。

## 2. 块做得更大，并没有更快

最直观的想法是：一次多处理一些 key，少循环几次，应该能减少调度开销。
当时把 key 块从 1024 扩到 2048，也尝试增加每块的 query 行数。

历史对照中，更宽的 key 块约慢 5%–8%，更多 query 行大体持平，更大的组合还碰到
片上空间和接口限制。减少循环次数并不等于减少主要工作量：每个分数仍要参与指数和归约，
更大的块也需要更多片上空间。这些因素解释了为什么扩大块不一定获益，但实验没有把
各项影响逐一分离，不能据此确定那 5%–8% 的具体来源。

因此保留每块 256 个 query、1024 个 key，转而检查各道工序如何配合。

## 3. 关掉一部分工作，才能看清重叠

诊断实验分别去掉矩阵乘法、向量计算、内存搬运，以及 softmax 或输出更新，
只留下维持执行顺序所需的信号。这些版本不再输出正确的 attention，仅用于理解流水。

早期对照中，只留下 Cube 的用时约为完整版本的 79%，只留下 Vector 计算的用时约为
81%。这纠正了一个容易出现的误判：删掉某项工作后只快一点，不代表它本身只花了这么
一点时间；它可能原本就与另一项工作重叠。性能分析也看到，一起运行时，若干搬运路径
比单独运行更慢。

接下来需要关注的是整体进度，而不是把各单元的忙碌时间相加，或把删除前后的差值直接
当成独立成本。这组观察来自早期融合 softmax 版本，不是对当前代码重新做出的逐项归因。

## 4. 多给一个周转槽，有帮助；再加就不明显了

既然两侧都有较多工作，增加一个工作区槽值得尝试：当旧槽尚未归还时，另一侧可能仍有
空槽可用，减少等待。历史融合 softmax 版本从两个槽改成三个槽后，三个输入规模上约快
3%–4%；增加到四个槽没有继续得到明确收益。

因此选择三个槽。这个结果也说明缓冲不是越多越好：它能让独立工作更早开始，
却不能消掉计算，也不能跳过数据依赖。这里的测量支持槽数选择，不能单独证明每一处
等待减少了多少。

## 5. 换成主线接口后，重新比较

早期实现依赖融合的 `SoftmaxFlashV2`。公开版本改用普通操作组成 softmax：求最大值、
减去最大值、计算指数、求和。这些归约接口来自 TileLang-Ascend PR #1852，现已合入
主线；示例不需要额外引入融合 softmax 扩展。跨块统计更新和延迟输出累加仍然保留。

接口改变会影响 Vector 的工作量和临时空间，不能直接沿用旧的槽数结论。
于是在新接口上，只改变工作区槽数，重新比较两个槽与三个槽：

| Batch / 序列长度 | 两个槽，ms | 三个槽，ms | 用时下降 |
|---|---:|---:|---:|
| 2 / 131072 | 1148.701 | 1125.264 | 2.04% |
| 2 / 65536 | 285.076 | 276.667 | 2.95% |
| 1 / 32768 | 35.650 | 34.511 | 3.20% |

表中单位是毫秒，用时下降以两个槽为基线。三个规模都通过当时的正确性检查，三个槽
都更快，因此公开版本保留“普通归约 + 三个槽”。这与旧接口下的 3%–4% 是两组独立
对照，不能相加成累计收益。

FP16 融合 softmax，以及融合缩放与转换的尝试，当时未能通过所需接口组成可运行的
完整候选，也没有被当成成功优化保留。

## 当前实现与测量边界

本示例使用 Expert 模式，手动安排计算、搬运和同步。输入输出及分数/权重工作区为
FP16；运行统计量、输出贡献工作区和输出累加为 FP32。它支持 MHA/GQA，不复制
共享的 K/V；固定头维度 128，要求序列长度是 1024 的整数倍、query 头数能被 K/V
头数整除，默认使用 24 个逻辑 Cube 核。

上述数字是 Atlas A3 上的历史对照，不是当前主线的新测量。普通归约的两槽/三槽比较
使用编译器提交 `77a444b2`；内部原始日志不随示例发布。本文依据已有整理记录说明
实现选择，不声称它在所有输入上最快，也不取代其他版本。

运行一个较小的正确性用例：

```bash
source ./set_env.sh
python examples/flash_attention/fa_opt/expert_v2/kernel.py \
  --B 1 --S 4096 --q-heads 12 --kv-heads 1 --D 128
```

性能比较可通过 `fa_opt/run.py --tl` 指定本文件。复测应保存编译器提交、输入形状、
设备与 CANN 版本，以及正确性检查和原始计时样本；更通用的方法见
[性能优化指南](../docs/optimization_guide_zh.md)。
