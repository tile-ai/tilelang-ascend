Kimi Delta Attention (KDA) 是 Kimi Linear 的线性注意力块：就是 Gated DeltaNet，
但遗忘门带上通道下标，于是块内衰减是一个 `K` 宽的向量，而不是每 token 一个标量。

### 性能测试

输入参数定义：

| Parameter | Value | Description |
|-----------|-------|-------------|
| B | 1 | Batch size |
| SEQ | 4096 / 8192 / 16384 | Sequence length |
| H | 4 / 8 / 16 / 32 / 96 | Query heads (`HV = H`, no GVA) |
| K, V | 128 | Key and value head dimension |
| C | 64 | Chunk size |
| BC | 16 | Anchor block inside a chunk |
| dtype | float16 / bfloat16 | Gate `g` is fp32 |

全部 float16。`route_b` 与 `KDA_WY_FIXEDCORE` 都是**默认关闭**、需显式开启，
所以“默认”一列是什么都不要的调用方拿到的：

|------|------|------|------|------|------|------|
| 4 | 4096 | 788.14u ±7.8 | 1422.57u ±3.1 | 55.4% | 854.68u ±4.9 | **92.2%** |
| 8 | 4096 | 1197.12u ±12.3 | 2457.73u ±9.7 | 48.7% | 1239.85u ±7.4 | **96.6%** |
| 16 | 4096 | 2010.82u ±14.1 | 4799.50u ±13.8 | 41.9% | 2374.75u ±34.3 | **84.7%** |
| 32 | 4096 | 3959.94u ±30.5 | 9559.25u ±7.0 | 41.4% | 4820.22u ±17.5 | **82.2%** |
| 96 | 4096 | 11423.01u ±13.4 | 28239.44u ±39.8 | 40.5% | 14270.49u ±68.4 | **80.0%** |
| 4 | 8192 | 1493.69u ±18.6 | 2807.97u ±24.7 | 53.2% | 1657.49u ±7.9 | **90.1%** |
| 4 | 16384 | 2995.36u ±39.7 | 5698.17u ±6.1 | 52.6% | 3369.31u ±50.6 | **88.9%** |

`H = 96` 是 Kimi K3 实际运行的头数。那里中位是 80.0%，三次采集跨 **79.80% ~ 80.57%**
——它是**压在线上**而不是稳在线上，换一天再采可能落到任一侧。两侧的趋势更有用：
**比值随头数下降**（`H = 8` 的 96.6% 一路到 `H = 96` 的 80.0%），**随序列长度基本不变**
（4096 时 92.2%，16384 时 88.9%）。让这个算子掉下去的是并行度，不是工作量。

`route_b` 在 `H = 96` 上比在 `H = 4` 上更值钱——1.96 倍对 1.63 倍——这和"固定开销"的直觉
正好相反。原因是**占比**：它改动的那两段在 `H = 96` 时占全流水 75%，在 `H = 4` 时占 65%。
所以这个算子的任何比值都必须报出头数。

bfloat16，只在这两个形状上采过。没有 bf16 的参考采集，故不给比值：

| H | 默认 | `route_b` |
|------|------|------|
| 4 | 1445.55u ±9.5 | 897.42u ±8.0 |
| 96 | 28380.11u ±2.2 | 14671.21u ±23.2 |

bf16 走 `route_b` 时在第六段绕了一趟 float32，因为这块硬件没有 bfloat16 的向量 select。
它在 `H = 96` 上端到端代价 1.5%、`H = 4` 上 3.4%。

`H = 96`、fp16 的逐段耗时：

| | cumsum | kkt | solve_tril | wy_fast | chunk_h | chunk_o |
|------|------|------|------|------|------|------|
| 默认 | 963.2u | 10084.9u | 1356.9u | 1704.8u | 3106.2u | 11117.1u |
| `route_b` | 955.7u | 3307.0u | 1353.8u | 1698.5u | 3084.7u | 4053.4u |
| `+ KDA_WY_FIXEDCORE` | 937.9u | 3326.6u | 1356.9u | **1506.2u** | 3087.8u | 4009.9u |

decode 路径按它自己的口径单独报告，因为厂商包没有 recurrent 算子可除。在
`H = HV = 96`、`K = V = 128`、fp16 下，`B = 1` 每步 115.50u、`B = 64` 每步 7152.52u——
3% 以内线性，说明它受算力约束、不受启动约束。它的标量流水占用 51.7%、向量流水才 46.5%，
那是这条路下一个值得优化的地方。

**测量方法。** `msprof` 完整形式（`msprof op` 在这台机器上返回 Task Duration 0.000000），
从 `op_summary` 读 device Task Duration。每个数字都是**三次独立采集的中位数**，每次 6 到 12 次迭代
（随形状而定），并丢弃第一次迭代——它带首次触碰开销，恒为离群点。同时给出
三次之间的半极差，好让读者知道这个数字值多少；同一配置的不同次采集每段可差到 25u，所以
这里没有任何结论建立在单次运行上。六段都编译成名为 `main` 的 `prim_func`、共享同一个
Op Name，靠启动顺序区分——一次 prefill 就是固定顺序的六次启动——并用 `Block Num` 佐证。
板子是 `Ascend910_9362`（910_93），20 个 AI 核。

本目录的 `bench.sh` 是另一件仪器：它 profile 的是每段自己的正确性扫描（混合形状），
回答的是“这一段有没有劣化”，不是“这个形状值多少”。

### 优化策略与影响分析

KDA 算子按下列顺序做了这些优化。每个行末标记是该步之后的绝对耗时（板上 `H = 4` 实测）
及其对参考实现的比值：

0. **正确但未优化** —— 按论文分解直接写出的六段流水  **--- 5992.20u，13.2%**
1. **指令向量化**：把否则会被降级成每行一条窄指令的广播显式物化  **--- 2417.41u，32.6%**
2. **算法上 Cube（kkt）**：锚定 `BC` 分解，把带门 Gram 矩阵的非对角条带变成一次普通矩阵乘
   **--- 1688u，46.7%**
3. **算法上 Cube（solve_tril）**：倍增 Neumann 级数，用 8 次矩阵乘替掉 62 行串行前代
   **--- 1584.83u，49.7%**
4. **冗余计算消除**：五刀，每一刀都是一件多余的工作——多数是同一个 kernel 上一行
   已经做过的事  **--- 1438.16u，54.8%**
5. **`route_b`**：对角块也加入 Cube 上的条带  **--- 874.74u，90.1%**
6. **`KDA_WY_FIXEDCORE`**：第四段按物理核数下发、而非按任务数  **--- 854.68u，92.2%**

其中收益最大的两条：

**指令向量化。** 一个缺了某个 `T.Parallel` 下标的操作数就是广播，本方言会把它降级成一个
循环（编译器命名 `outer_broadcast_idx`）里每行一条窄指令，每条前面还带一个屏障。改成
`T.tile.broadcast` 到一个此刻已死的 tile 上，就变成一条宽指令铺开，且不额外占 UB。
在隔离的微基准上实测 1866.80u -> 122.46u，逐位相同。

**把 Gram 矩阵放上 Cube。** 门是逐通道的，衰减就落在对 `d` 的求和里面，于是
`sum_d k_i[d] k_j[d] exp(g_i[d] - g_j[d])` 不是一个矩阵乘。把指数在锚行 `a` 处劈开，
可以分解成一个只含 `i` 的因子和一个只含 `j` 的因子，两者分别折进两个操作数，剩下就是普通的
`X Y^T`。对非对角条带两个因子都有界；对对角块列因子无界——这正是它们在 `route_b` 之前一直
留在向量单元上的原因。`route_b` 把那个列因子的钳位抬高，并把 Cube 操作数换成 bfloat16，
用它的指数范围兜住。**默认关闭**，因为这是一个近似：一个陡到块内跨度超过钳位的门会饱和。它在 `cu_seqlens`
下也不可用——varlen 调用若请求它，会退回路线 A 并发出告警。

**为什么没有做算子融合。** 三件事都试过并实测过，记在这里免得再试一遍：

- **在这块板上，Cube↔Vector 的交接都要走一趟 GM，和两半是否同处一个 kernel 无关。**
  `T.copy(ub, l1)` 在这里不产生 UB→L1 搬运：生成的 AscendC 里 `copy_ub_to_l1` 计数为
  **0**，本机缓存的 72 个 kernel 里也全是 0（对照 `copy_gm_to_l1` 267 次）。这不是"静默"
  ——`AscendWorkspaceReduction`（`tilelang/engine/phase.py:83`）把它改写成两段经 GM 的
  拷贝，教程明写该 pass 默认常开。**开关只有一行**：
  `needs_gm_workspace_ = (platform != "A5")`
  （`src/transform/ascend_workspace_reduction.cc:137`）——**A5 保留直通路径，A3（本板）
  没有**；`pto_use_pipe` 这个 flag 也救不了，因为那里的判断是 `||`。
  所以代价挂在 **AIC/AIV 的边界**上、不是 kernel 边界上，把两段塞进一个 kernel 消不掉它。
  换到 A5 上这一条需要重测。
- **就算能融，段间也没有空档可回收。** 六次启动在同一条流上串行，段间那五个间隙实测
  每个 2.5~10us、合计约 **21us**，对 14459.51us 的整段 prefill 是 **0.15%**。
  融合是在回收一段根本不存在的空闲。官方 PyPTO 实现也得出同样结论：它同样把
  `gk`、`aqk`、`akk`、`w`、`u`、`qg`、`kg`、`v_new`、`h` 全部落在 GM。
- **Cube 侧 multi-buffer 正确但零收益。** `aic_mac` 占用率只有 4.2%，更深的流水没有东西
  可藏。这里是**占用率证据胜过指令形态证据**。

真正剩下的是**同步**和**每块序幕**。第六段有 30.8% 花在同步上——这个数是把同步插入器关掉
重新构建测出来的，那样数值是错的，但能给屏障计时——而且它十八对 `SetFlag` / `WaitFlag`
每一对都是置位后紧接着等自己，所以没有任何东西被重叠掉。六段合计 14459u 里有 4561u 在标量
单元上，而且那是每块的序幕开销、不是算术：第四段 6144 个块，每块运行 277 ns，序幕就要
164 ns。`KDA_WY_FIXEDCORE` 就是把这个观察用在一段上，另外五段还没做。

### 参考实现

对标的 AscendC 算子是 `chunk_kda_fwd`：
https://gitcode.com/cann/ops-transformer/tree/master/attention/chunk_kda_fwd

它不在 CANN 二进制发布包内，是从上述源码仓构建的。两侧跑相同形状、相同 dtype。

它运行在 `safeGate = 1` 配置下——那是它的快档，也是本文件每一个比值的分母。该开关把 score
操作数从 fp16 换成 bfloat16（`chunk_kda_fwd_prepare.h:167`）、把三角求解的流水深度从 1 提到
4（`:224`）、并走一个软件流水化的任务循环（`:2331`）。

这里用的形状命中 `TilingKey 2`，即 `chunkSize == 64 && kDim == 128 && vDim == 128` 的
编译期特化。在本硬件上这个 key 仍然派发到通用实现：arch35 特化的门条件是
`__CCE_AICORE__ == 310`，那是 Ascend950。
