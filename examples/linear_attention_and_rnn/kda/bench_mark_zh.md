# KDA 性能测试

Kimi Delta Attention (KDA) 是 Kimi Linear 架构中的线性注意力层。它在 Gated DeltaNet
的基础上只改了一处：遗忘门带上了通道下标，因此 chunk 内的衰减是一个 `K` 宽的向量，
而不是每个 token 一个标量。本目录用 TileLang 在昇腾上实现了它的解码递推和 chunkwise
预填充前向。

## 性能测试

输入参数定义：

| Parameter | Value | Description |
|-----------|-------|-------------|
| B | 1 | Batch size |
| SEQ | 4096 | Sequence length |
| H | 4 / 8 / 16 / 32 / 96 | Query heads (`HV = H`, no GVA) |
| K, V | 128 | Key and value head dimension |
| C | 64 | Chunk size |
| BC | 16 | Anchor block inside a chunk |
| dtype | float16 | Gate `g` is fp32 |

`H = 96` 是 Kimi K3 实际使用的头数。

最佳性能结果，对标参照实现的 `safeGate = 0` 配置（见下文 **参照实现** ——
那是它的回退路径，不是快速路径）：

| H | AscendC | tileLang | Performance Ratio (AscendC/tileLang) |
|------|------|------|------|
| 4 | 1141.78u | 1183.30u | 96.5% |
| 8 | 1884.56u | — | — |
| 16 | 3437.45u | — | — |
| 32 | 6855.00u | — | — |
| 96 | 20180.92u | 21508.20u | 93.8% |

不开 `route_b`（默认配置，见下文）时的比值是 `H = 4` 上 79.4%、`H = 96` 上 71.0%。
比值从 `H = 16` 往上趋于稳定：参照实现的固定开销更大，在小 `H` 上占其运行时间的
19.0%，而我们只占 13.2%，这个差别正是 `H = 4` 上比值偏高的原因。用
`T = fixed + rate * waves` 拟合头数阶梯，本实现是 190.3u + 90.57u/wave，参照实现是
217.2u + 64.93u/wave，因此两者边际速率所对应的稳态比值是 71.7%。

对标参照实现的 `safeGate = 1` —— 那才是它真正更快、且精度相当的配置 ——
在为它采集的两个形状上：

| H | AscendC `safeGate=1` | tileLang | Ratio (AC/TL) | tileLang (`route_b`) | Ratio (AC/TL) |
|------|------|------|------|------|------|
| 4 | 783.05u | 1438.16u | 54.4% | 1183.30u | 66.2% |
| 96 | 11414.79u | 28406.60u | 40.2% | 21508.20u | 53.1% |

以上四行来自同一次采集；同一次运行中 `safeGate = 0` 的读数是 `H = 4` 上 1130.66u、
`H = 96` 上 20117.76u，比上表低约 1%，这是本机的重复采集离散度。

这段差距全部来自软件流水，而本实现完全没有做：参照实现的快速路径带有 4 级流水的
三角求解和一个软件流水化的任务循环，两者都在本仓库自己的优化清单
（`examples/flash_attention/fa_opt/`，第 3 项与第 5 项）上，属于本实现尚未开始的工作。
本实现做的是算法层面的事：锚行分解与倍增 Neumann 级数把两个原本不是矩阵乘的阶段搬上了
Cube —— 这一项不在那份清单上，因为 flash attention 本身就已经是矩阵乘了。

长序列，`H = 4`：

| SEQ | AscendC | tileLang | Performance Ratio (AscendC/tileLang) |
|------|------|------|------|
| 4096 | 1123.11u | 1416.43u | 79.3% |
| 8192 | 2199.11u | 2818.35u | 78.0% |
| 16384 | 4434.27u | 5500.72u | 80.6% |

### 解码路径

单独给出，而且只能按它自己的口径给：厂商包里只有 `chunk_kda_fwd`，没有 recurrent
算子，因此没有可除的对标物。这条路上有意义的轴是 batch 而不是长度——一次解码步就是每
条序列一个 token——而 grid 是 `B * HV`，所以在 K3 的头数下 `B = 1` 就已经把 96 个 block
铺到了 20 个核上。

`H = HV = 96`、`K = V = 128`、fp16、带非零 `initial_state`：

| Configuration | 每步时长 | Blocks | 相对 `B = 1` |
|------|------|------|------|
| `B = 1`, `SEQ = 1` | 115.50u | 96 | 1.00x 做 1x 的活 |
| `B = 8`, `SEQ = 1` | 896.72u | 768 | 7.76x 做 8x 的活 |
| `B = 32`, `SEQ = 1` | 3583.99u | 3072 | 31.03x 做 32x 的活 |
| `B = 64`, `SEQ = 1` | 7152.52u | 6144 | 61.93x 做 64x 的活 |
| `B = 1`, `SEQ = 8` | 859.40u | 96 | 短 prompt 走这条路 |

扩展性线性、误差 3% 以内，且略优于线性，说明即使在 `B = 1` 这条路也是受计算量约束
而非受启动约束。

流水占用，以及这条路为什么是下一个值得优化的目标：

| Configuration | vec | scalar | mte2 | mte3 | cube mac |
|------|------|------|------|------|------|
| `B = 1`, `SEQ = 1` | 0.465 | **0.517** | 0.034 | 0.022 | 0.000 |
| `B = 64`, `SEQ = 1` | 0.458 | **0.504** | 0.054 | 0.022 | 0.000 |

Cube 一栏为零是设计使然：这里每个 token 级运算都是矩阵-向量形状（`M = 1`），填不满
16x16x16 的 fractal，因此该 kernel 不分配 L0/L1、也不发 `T.gemm_v0`。何况解码本来就是
访存受限的。

真正的发现是标量占用。51.7% 已经超过向量流水自己的 46.5%，也远过本仓库调优笔记给出的
35% 这条线——过了这条线意味着 kernel 在忙着发指令而不是在算。同一个特征在预填充侧被
处理时（把广播物化）值 3575u。这条路从未做过那一遍。

## 优化策略与效果分析

`H = 4` 上的优化轨迹，每一步都在板上实测。比值列与第一张表一样，对标
`safeGate = 0`：

| Step | Optimization | Time | Ratio (AscendC/tileLang) |
|---|---|---|---|
| 0 | 正确但未优化 | 5992.20u | 19.1% |
| 1 | **指令向量化** —— 把会被降级成每行一条窄指令的广播显式物化 | 2417.41u | 47.2% |
| 2 | **kkt 上 Cube** —— 锚块 `BC` 分解把非对角条带变成普通矩阵乘 | 1688u | 67.6% |
| 3 | **solve_tril 上 Cube** —— 倍增 Neumann 级数把 62 行串行前代换成 8 次矩阵乘 | 1584.83u | 72.0% |
| 4 | **删除冗余** —— 五刀，每一刀都是另一个阶段已经做过的工作 | 1438.16u | 79.4% |
| 5 | **`route_b`** —— 对角块与条带一起搬上 Cube | 1183.30u | **96.5%** |

对贡献最大的两项的说明：

**指令向量化。** 一个操作数如果缺少 `T.Parallel` 的某个下标，它就是一次广播，而本方言
会把它降级成一个循环内每行一条窄指令（编译器把这个循环命名为 `outer_broadcast_idx`），
每条前面还带一道屏障。改成 `T.tile.broadcast` 写进一块此刻已经无用的 tile，就变成一条
宽指令铺开，且不额外占用 UB。在独立的微基准上实测 1866.80u -> 122.46u，结果逐位相同。

**把 Gram 矩阵搬上 Cube。** 由于门是逐通道的，衰减落在对 `d` 的求和里面，所以
`sum_d k_i[d] k_j[d] exp(g_i[d] - g_j[d])` 不是矩阵乘。在锚行 `a` 处把指数劈开，就分解成
一个只含 `i` 的因子乘一个只含 `j` 的因子，两者各自吸进两个操作数，剩下一个普通的
`X Y^T`。对非对角条带来说两个因子都是有界的；对对角块来说列因子无界，这就是它们在
`route_b` 出现之前一直留在向量单元上的原因。

`route_b` 放宽了对该列因子的钳位，并把 Cube 操作数换成 bfloat16 —— 它的指数范围装得下。
它默认关闭：它是一个近似，门陡到在一个块内跨度超过钳位值时会饱和。门形状正常的调用方
传 `route_b=True` 就能在这个阶段拿到 2.3 倍；不主动要求的调用方则保持本算子交付时的
数值行为。

## 正确性

每个阶段都对照两个互相独立的 CPU 真值：逐 token 的递推，以及一份按论文分解式写出的
chunkwise 参考实现。两个真值之间的一致程度会一并给出，因为那是本 kernel 所能达到的下界。

有三条性质是按精确相等断言的，不是按容差：

- 一个 varlen 批次与把每条序列单独跑，结果逐位相同；
- 一条序列在 chunk 边界切开分两半跑，与整条跑，结果逐位相同；
- 传入全零的 `initial_state` 与不传，结果逐位相同。

`SEQ = 4096` 上对逐 token 真值的相对误差：fp16 为 8.4e-4，bf16 为 6.7e-3，
两者都约为各自格式输出量化底噪的 1.7 倍。

## 参照实现

*AscendC 参照实现源码：*
https://gitcode.com/cann/ops-transformer/tree/master/attention/chunk_kda_fwd

参照实现不在 CANN 二进制发行包内，是从该源码仓库构建的。两侧跑同样的形状、同样的 dtype。

参照实现有两种配置，而且相差很远。`safeGate = 1` 把 score 操作数从 fp16 换成 bfloat16
（`chunk_kda_fwd_prepare.h:167`），把三角求解的流水深度从 1 提到 4（`:224`），并走一个
软件流水化的任务循环（`:2331`）。在本机实测，它在 `H = 96` 上比 `safeGate = 0` 快
1.76 倍（11414.79u 对 20117.76u），在 `H = 4` 上快 1.44 倍（783.05u 对 1130.66u），
而其输出与 `safeGate = 0` 在 fp16 量化精度内一致：

```
safeGate=0   attn_out[0:4] = -0.000518 0.000986 0.022263 -0.002504
safeGate=1   attn_out[0:4] = -0.000509 0.000983 0.022263 -0.002506
```

而且它申请的 workspace 更大（109.39 MB 对 104.47 MB），说明它做的是更多的缓冲而不是更少
的计算。所以 `safeGate = 0` 是回退路径而非快速路径，上文两者都已给出。

这里使用的形状命中 `TilingKey 2`，即 `chunkSize == 64 && kDim == 128 && vDim == 128` 的
编译期特化。但在本硬件上该 key 仍然分派到通用实现：arch35 特化的条件是
`__CCE_AICORE__ == 310`，那是 Ascend950。

测量方法：`msprof` 采集的设备侧 Task Duration，取自 `op_summary`，丢弃首次启动（冷启动），
其余热启动取中位数。六个阶段都编译成名为 `main` 的 `prim_func`，因此共用同一个 Op Name，
只能按启动顺序区分——一次预填充是固定顺序的六次启动，`Block Num` 可以佐证。`bench.sh`
是另一件仪器：它采的是每个阶段自己的正确性套件（一堆混合形状），回答的是「这个阶段有没有
退化」，而不是「这个形状值多少」。硬件为 `Ascend910_9362`（910_93），20 个 AI Core。同一配置的多次采集
每个阶段可相差最多 25u，因此上表中每一组 A/B 都取至少三次采集的中位数。
