# Expert v2：把私有短序列接进共享前缀流水

本目录是新增的 v2 实现，不替换已有的 [非分页](../expert_v1/kernel.py)或[分页](../expert_v1/paged.py) v1。
与它们的区别见[目录说明](../README.md)。

[`kernel.py`](kernel.py) 计算这样一种 attention：同一请求下的多个候选序列（beam）
共享一段较长的历史 K/V，但每个 beam 还有自己的两个新 token。每个 query 都要对
“共享前缀 + 自己的新 token”做一次完整 softmax，再对 value 加权求和。
它不是分别算出两个归一化输出后取平均。

这里长短两部分差别很大：共享前缀有 1024 或 2048 个 token，私有部分只有两个。
在昇腾上，Cube 单元擅长矩阵乘法，Vector 单元负责向量计算。下面的优化围绕一个
问题展开：怎样利用共享数据，又不让极短的私有部分拖慢整条流水？

## 1. 长的部分用矩阵乘法，短的部分不必照搬

最初的完整实现分别安排共享和私有计算，再合并结果。为观察共享部分是否还有改善空间，
实验先暂时移除私有部分，单独研究分块计算、在线 softmax 和输出累加的流水。
这些版本只是诊断工具，功能不完整，不能拿它们的更短用时声称完整 XA 更快。

接下来的完整方案让所有参与核先处理共享前缀，再用 Vector 计算每个 beam 的两个私有
token。这样不必为很短的计算单独保留一组 Cube 核。合并时保留两部分的最大分数、
指数和与未归一化输出，先把它们缩放到同一个最大值，再一起归一化，保证仍然是完整
序列上的一次 softmax。

历史实验中，这个两阶段方案在大输入上有收益，小输入却未必：18 个用例的用时之和
下降约 2.3%，但只有 6 个用例更快。第一阶段结束后要全局同步，再启动第二阶段，
这些开销在小输入上更显眼。直接把私有部分的小矩阵乘法拼到共享 Cube 流水里的另一
尝试也没有胜出；同批次对照的用时之和反而增加约 3.9%。最终继续采用 Vector 处理短尾。

## 2. 先让下一块能进来，再消掉整个第二阶段

两阶段方案还有一处可以提前放行：数据加载后，若计算一直占着载入槽，下一块就不能
进入。先把所需数据转到计算用的临时空间，再归还载入槽，能够给下一块搬运与当前计算
重叠的机会。这个改动在一次完整对照中让 18 个用例都更快，用时之和下降约 4.2%。

随后才进一步融合。共享部分处理完最后一个 key 块时，输出和统计量本来就还在片上。
与其把它们写回全局内存、同步、再读回来，不如就在这一刻计算私有部分并合并输出。
每个核直接完成自己负责的行，不再需要等待所有核进入统一的第二阶段。

这一步也调整了私有 K/V 的处理顺序：一次处理同一个 query 头对应的 32 个不同 beam，
而不是为了多个共享同一 K/V 的 query 头，先把私有 K/V 展开成多份。少做了数据复制，
也避免为融合再申请一整套片上缓冲区。

复用旧缓冲区并不是随意覆盖：会被载入覆盖的数据只在占有载入槽时使用，最终输出复用
原来的写出槽；需要跨越载入槽释放点的统计量则放在不会被搬运覆盖的空间。
历史对照中，就地合并进一步减少了约 4.6% 的总用时，但并非每个输入都获益。

## 3. 去掉统计量的来回转换，再减少大矩阵上的工作

合并计算需要的每行最大值与指数和，在片上原本以重复八次的形式保存，后面的逐行缩放
也需要这种形式。旧实现却先把它归约成一个标量，算完后再广播回八份。
既然八份数值相同，就让整条统计计算保持这个形式，省掉归约和广播往返。
连同这一阶段的其他小调整，历史对照的总用时下降约 2.0%。

原来的期待是少发几次向量操作就能明显变快，但收益没有按操作条数等比例增长。
于是下一步不再只数操作，而是检查每一步处理了多少数据：

- 把输出矩阵上的归一化除法移到每行的小系数上，再用系数缩放输出；
- 把 query 向量上的缩放移到点积之后的少量分数上；
- 先把最终合并系数乘进私有权重，避免对整张私有输出再缩放一次；
- 把两个 token 的转换和逐行缩放合在一起提交。

这些变换不改变 attention 的数学目标，但会改变浮点计算顺序，因此仍需检查正确性。
最终同批次对照中，18 个用例都更快，总用时下降约 4.7%。这支持这些具体改动，
不意味着可以给所有向量操作套用一个固定的硬件成本。

## 4. 算术没有变，少读几次数据也有收益

合并尾部的诊断实验又发现，去掉两段读取带来的用时变化很不对称。这个结果提示需要
检查读取何时发生、是否有其他计算可以重叠，而不是只按搬运字节数估计成本。
消融得到的是删掉工作后暴露出来的时间变化，不能把各项差值当作可相加的独立成本。

检查索引后发现，同一 beam 的私有 K/V 被不同 query 头重复读取。只要这份数据仍在
片上，就可以让它们共用；同时，把下一组 query 的读取提前到已有的小统计计算期间。
共享前缀只有一个 key 块时，还能跨相邻输出片复用私有 K/V。若有多个 key 块，
中间载入共享输出会覆盖这片复用空间，所以不能把这个条件省掉。

最终版本没有靠少算 attention 获益：主要改变的是数据读取次数和时机。
四次完整历史对照中，它都比前一版在 18 个用例上更快，总用时下降约 1.9%–2.3%。
这就是选择 `tl_xattn_v3q` 作为本示例来源的主要依据。

## 5. 没有采用的方案，也解释了最后的选择

更多缓冲并不总能容纳。当时评估过再加一个载入槽、同时合并更宽的输出片，以及让
多 key 块输入也跨片保留私有 K/V；它们所需的临时空间与现有数据生命周期冲突，
没有成为可运行、可比较的候选，不能写成已测得的失败速度。

还有一条为接口兼容而手工展开 softmax 的历史分支，通过了正确性，但在两次完整对照
中总用时约增加 19%，因此没有作为性能后继版本保留。这只说明当时那种展开方式没有
胜出，不说明所有普通归约实现都慢。

后来主线归约接口变化，本示例改用求最大值、减法、指数与求和组成在线 softmax，
逐行缩放按 64 列分段调用。当前研究源中的 `q` 和 `q_chunked` 算法已相同；不同批次
计时约 0.5% 的差距不能用来认定 `q_chunked` 是更快的新算法。

## 怎么读这些性能数字

下表保留三个关键选择的同批次对照。单位为微秒，是 18 个用例各自平均设备用时的
合计，不是一次完整业务请求的延迟；下降比例均以该行的前一方案为基线。

| 改动 | 前一方案，us | 新方案，us | 合计用时下降 |
|---|---:|---:|---:|
| 独立第二阶段改为就地合并 | 9733.95 | 9282.41 | 4.64% |
| 把大矩阵上的缩放移到小系数/分数上等调整 | 9077.62 | 8651.58 | 4.69% |
| 减少重复载入并调整读取时机 | 8684.28 | 8488.77 | 2.25% |

三组分别对应历史 `f → m`、`n → p`、`p → q`，不是连续同批次测试，不能把百分比
相加或相乘成累计收益。逐用例数据摘录见
[`history_measurements.csv`](history_measurements.csv)，保留了原报告名、计时与正确性结果。

这些是 2026 年 7 月研究版本的历史测量；原报告没有保存源码哈希或完整编译器身份，
而研究源在 9 月又改过接口，因此不能当成当前主线代码的性能保证。
历史整体表现支持选择 q 这条完整实现，但不证明它在每个输入、每台设备上都最快。

## 当前示例与运行方式

这是 Expert 模式的完整实现，不依赖本地研究仓或 xLLM 扩展。输入输出为 BF16，
softmax 与输出累加使用 FP32；32 个 query 头共享 8 个 K/V 头，头维度为 128。
每个 beam 恰好有两个私有 token；共享长度须为 1024 的整数倍，每请求 beam 数须为
64 的整数倍。公开示例默认使用 24 个逻辑 Cube 核，历史研究版本使用 20 个。

五个输入依次为 query、共享 key、共享 value、私有 key、私有 value。
设请求数为 R、每请求 beam 数为 B、共享长度为 S，它们的形状依次是
`[R*B,32,128]`、两份 `[R*S,8,128]`、两份 `[R*B,8,2,128]`；
输出为 `[R*B,32,128]`。共享 K/V 直接复用，不按 beam 复制。

```bash
source ./set_env.sh
python examples/xattention/expert_v2/kernel.py
# 原研究问题的 18 个输入形状，仅检查本示例，不运行全量算子测试：
python examples/xattention/expert_v2/kernel.py --all-cases
```

默认检查两个输入，覆盖单 key 块与多 key 块处理；参考实现对拼接后的完整序列计算
一次 softmax。`bench_test.sh` 会自动发现并运行本目录的 `kernel.py`，
README 和 CSV 不会执行。
