# Expert v3：先验证 CCE 调度，再用 TileLang 表达

这条路线希望把手写 CCE 版已经验证过的流水组织，用现有 TileLang 接口表达出来。
矩阵乘法交给 Cube，softmax 和输出更新交给 Vector。两者是芯片上不同的计算单元，
可以同时工作。输入和输出仍是 FP16，Vector 的中间运算和输出累加使用 FP32。

它是独立的新实现，运行入口为 [`kernel.py`](kernel.py)。
v2 从 TileLang 的写法出发组织高性能流水；v3 则先用 CCE 写出并验证计算和调度，
再考虑怎样用 TileLang 表达。不能直接表达的部分，用现有原语组合或拆分处理。
这两版的区别是设计起点，不只是版本号先后。
下面的“优化前”和“优化后”都指这条实现，不是旧流式版本的历史成绩。
v2 的分块和流水槽实验见[另一篇历程](../expert_v2/README.md)。

## 1. 先把搬运和计算的空间分开

长序列 attention 每次只处理一部分 key。除了计算当前块，还要读取下一块、
写出上一块。如果它们争用同一片存储，即使硬件有独立的搬运单元，也只能互相等待。

因此，新版给输入和输出各准备两个搬运槽。计算读一个输入槽时，另一个可以接收
下一块数据；计算生成输出时，上一个输出可以继续写回。运行中的输出累加留在
片上向量存储区，避免每处理一个 key 块都把整个累加值写出去再读回来。

与此同时，Cube 与 Vector 之间保留三个完整工作区槽。一个槽里的分数被改成权重，
随后供矩阵乘法使用；输出贡献和对应的缩放系数也保留到真正消费它们的时候。
跨 query 任务延续同一条流水，不在每个任务边界都排空重启。

这些结构让重叠成为可能，却不保证实际已经最快。下一步需要看哪些工作占据了时间。

## 2. 为什么先检查 Vector

在序列长度 32768 的输入上，优化前完整用时约 31.3 ms。性能分析显示，
Vector 的忙碌时间约 28.1 ms，矩阵乘法约 18.8 ms。

这些时间有重叠，不能相加。为了确认方向，实验保留搬运和同步信号，
去掉 Vector 的主要计算，完整用时降到约 24.7 ms。这个诊断版本不能得到正确的
attention，但它说明：减少 Vector 路径上的成本，确实有机会缩短总时间。

检查代码后，没有发现任务边界反复排空，也没有发现某个大锁强迫整条流水串行。
因此本轮先研究 Vector 内部的工作顺序，没有继续增加缓冲区。

## 3. 有些等待可以用有效计算填上

Vector 指令写完结果后，后续指令需要隔一段时间才能安全读取。早期实现为了保证
正确性，在一些短依赖之间插入了固定数量的空指令。

问题在于，程序里还有本来就要做的工作。例如，softmax 要把每个分数乘上一个
固定的正数，也要找最大值。先找最大值再缩放，与先缩放所有分数再找最大值，
得到的最大值相同。

利用这一点，新版把缩放拆成几段，安排到最大值更新、缩放系数和广播之间。
广播就是把每个 query 的一个数，准备成后续整行计算方便读取的形式。
需要等待时，硬件可以做这些必要计算，而不是执行空指令。

另一处等待出现在“减最大值”与“求指数”之间。逐个元素检查读写顺序后发现，
前面的分块遍历已经提供了间隔。删除额外填充，再通过实际生产路径检查数值，
也得到了收益。

最后，减最大值时的两路输入还有地址布局上的竞争。新版为广播系数保留两份
内容相同、地址不同的副本，让每个窗口选择更合适的一份。这项收益较小，
但叠加到前两项之后仍有净加速，因此一起保留。

## 4. 指令更少，为什么也可能没有收益

本轮也验证了几项直觉上合理、最终没有采用的改动。

| 尝试 | 当时为什么想试 | 实际结果 |
|---|---|---|
| 转换和缩放在两个存储区域之间往返 | 希望减轻原地读写的竞争 | 完整用时没有净改善 |
| 在每行末尾留一点空隙 | 让求最大值、求和的第一步从 64 条短指令变成 8 条长指令 | 转换、指数和写出准备变得更碎，整体没有变快 |
| 合并连续的 K 搬运 | 用一条长搬运替代八条短搬运，减少指令和地址计算 | 搬运指令确实减少，但当前完整算子没有净加速 |

这些结果说明，某个局部看起来更省，并不等于整条流水更快。要同时检查它给其他
步骤增加了什么代价，以及当前真正拖慢总进度的是哪条路径。

系数布局也不是“消除了所有冲突”：一类存储冲突指标下降，另一类却上升。
它被保留，是因为完整算子更快，而不是因为单个地址公式看起来更漂亮。

## 5. 最终留下了什么

最终版本保留了必要计算的重新排序、删除重复等待，以及两份错开存储位置的广播系数。
分块大小、输入输出搬运量、流水槽数和任务分配都没有改变。

| Batch / Length | 优化前，ms | 优化后，ms | 用时减少 |
|---|---:|---:|---:|
| 2 / 131072 | 1019.656 | 954.812 | 6.36% |
| 2 / 65536 | 250.257 | 233.315 | 6.77% |
| 1 / 32768 | 31.273 | 29.161 | 6.76% |

三个输入上，优化后与优化前的输出逐位相同，并通过参考 attention 检查。
32K 输入的 Vector 忙时从约 28.14 ms 降到 25.85 ms，矩阵乘法仍约 18.8 ms，
支持本轮收益主要来自 Vector 内部调度的判断。

目前仍慢于手写 CCE FP32。继续压缩个别等待或修改地址的收益正在减小；
进一步的大改应研究求最大值、求和的接口怎样与其他计算配合，检查完整流水的收益。

## 用 TileLang 表达时的取舍

这里移植的是 CCE 中验证过的工作组织，不是逐条抄写所有底层指令：
保留输出累加常驻 UB、独立输入/输出搬运槽、跨 query 延续流水，以及明确的缓冲归还顺序；
矩阵计算、归约和逐行缩放仍通过已有 TileLang 接口生成。

有些细节需要拆开表达。例如，逐行缩放按 64 列窗口调用行广播原语；
先显式准备广播系数，再使用不带临时广播工作区的形式，保留所需的地址和执行顺序。
部分生产者与消费者之间的间隔由必要计算提供，仍需额外间隔的输出更新路径沿用已验证的
短操作序列，不把它解释为通用延迟公式。矩阵乘法与结果导出使用 UnitFlag 衔接。

最大值与求和保留主线 `T.reduce_max/sum`，并未把 CCE 的全部归约指令展开搬进示例。
源码不注入目标代码，也不依赖新增编译器功能。具体顺序、地址、scratch 和同步只在
记录的输入与环境下验证；修改它们以后要重新检查正确性与完整用时。

## 运行与修改

输入输出为 FP16，非因果 MHA/GQA，固定头维度 128；query 长度是 256 的整数倍，
key/value 长度是 512 的整数倍，query 头数能被 K/V 头数整除。CLI 使用相等的
query/key 长度，默认 24 个逻辑 Cube 核。FP32 中间计算不表示支持任意数值范围。

```bash
source ./set_env.sh
python examples/flash_attention/fa_opt/expert_v3/kernel.py
```

`run.py --tl expert_v3/kernel.py` 可选择本版；默认仍保留 v2。
`bench_test.sh` 自动发现本目录的 `kernel.py`，不会执行更深一层的生成工具。

[`kernel.tl`](kernel.tl) 是含 LOCK 声明的可编辑源，
`kernel.py` 是生成结果，不直接编辑。LOCK 表示缓冲区在两条流水线间的占有权交接，
覆盖初始化、取用、归还和退出时的 drain；它不是通用互斥锁。
修改后从仓库根目录执行：

```bash
python examples/flash_attention/fa_opt/expert_v3/tools/preprocess.py \
  examples/flash_attention/fa_opt/expert_v3/kernel.tl \
  -o examples/flash_attention/fa_opt/expert_v3/kernel.py
ruff format examples/flash_attention/fa_opt/expert_v3/kernel.py
```

默认关闭的中间结果记录路径仅供诊断，不参与正常计时。
