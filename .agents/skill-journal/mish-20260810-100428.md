# Skill Feedback - mish（基于官方达标版本 0.7168，补正面案例）

> 本 journal 基于一次完整的 mish 算子开发：Stage 1-3 全流程，5 轮性能调优迭代，官方 cann-bench 测评 mean speedup **0.7168**（目标 ≥ 0.6 达标）。与同目录 `mish-20260807-154500.md`（性能灾难版 0.0159）形成对照——同一算子两版结果差异源于数值稳定方案的选型，该经验对 `tilelang-op-design` 等 skill 有重要补强价值。

## Entry e1
- **target_skill**: tilelang-op-design
- **target_artifact**: skill
- **target_section**: 数值稳定性方案设计章节
- **type**: missing_constraint
- **severity**: high
- **status**: applied

**Observation**:
数值稳定方案选型时，skill 没有强制要求"优先用数学等价变换消除条件分支"。同一 mish 算子的两版实现证明这是决定性的：
- 性能灾难版用 `T.if_then_else` 条件分支（x < -8 用近似公式）→ 无法向量化，降级为串行循环（每 tile 8192 次标量迭代）→ 官方 speedup 0.0159
- 官方达标版用 log-sum-exp trick（`softplus = max(x,0) + ln(1+exp(-|x|))`）→ 全 `T.tile.xxx` 向量化 → 官方 speedup 0.7168

差距 **45 倍**，根因纯粹是数值稳定方案是否引入条件分支。

**Evidence**:
- 性能灾难版 `custom/mish/history_version/mish_impl_s2_attempt1.py` L152-158 用 `T.if_then_else`，本地 bench 0.0159
- 官方达标版 `custom/mish/mish.py` L113-129 全 `T.tile.xxx`（abs/mul/exp/add/ln/max/sigmoid/sub/mul），官方 cann-bench iter3 mean speedup 0.7168（`custom/mish/perf_tuning/cannbench_official_iter3.json` L54 `"avg_speedup": 0.7167978725443414`）
- `DESIGN.md §1.4 阶段一` 明确写："直接公式 `ln(1 + exp(x))` 在大正数 x 时 `exp(x)` 溢出...采用数值稳定等价公式 `softplus(x) = max(x, 0) + ln(1 + exp(-|x|))`"——这是 log-sum-exp trick 的标准应用，消除了所有条件分支

**Proposed change**:
在 `tilelang-op-design` SKILL.md 数值稳定性方案设计章节新增硬约束："数值稳定方案选定后，**必须评估其对向量化的影响**。若方案依赖 `T.if_then_else` 逐元素条件分支，**必须先探索数学等价变换**（如 log-sum-exp trick、分段多项式逼近、`tanh(s) = 2*sigmoid(2s)-1`）消除分支。只有当所有等价变换都不可行时，才允许用条件分支，并在设计文档显式标注'此方案会导致串行循环，性能代价 X'。参考案例：mish 算子用 `softplus = max(x,0) + ln(1+exp(-|x|))` 消除大值域 exp 溢出的条件分支，全向量化实现官方 speedup 0.7168。"

## Entry e2
- **target_skill**: tilelang-perf-optimization
- **target_artifact**: skill
- **target_section**: element-wise 算子 host 侧 tiling 优化决策树（建议新增章节）
- **type**: missing_api_doc
- **severity**: high
- **status**: applied

**Observation**:
mish 官方 speedup 从 0.5932（baseline）提升到 0.7168（达标），**+20.5% 全部来自 host 侧 adapter 优化，不是 kernel 优化**。这两轮优化是 element-wise 算子的通用 pattern，但 `tilelang-perf-optimization` 的 `cann-bench-elementwise-optimization.md` 没有把它们系统化成决策树：
- iter2（1D shape block_N cap 512→8192）：case 12 speedup 0.076→0.570（+650%），mean +13.6%
- iter3（ND smart-flatten 搜索 split point 最小化 num_blocks）：case 13 speedup 0.220→0.714（+224%），mean +6.4%

**Evidence**:
- `custom/mish/perf_tuning/optimization_log.md` Iteration 2/3 完整记录
- `custom/mish/Mish/cann_bench/mish.py` L91-99：`if M <= 2: max_bn = min(N, 8192)`（1D shape 提升 block_N cap）
- `custom/mish/Mish/cann_bench/mish.py` L235-265：ND smart-flatten 搜索所有 split_idx 选最小 num_blocks
- 官方测评对比：iter1 baseline 0.5932 → iter3 0.7168（`cannbench_official_iter3.json`）
- 本质：element-wise 算子 kernel 时间已接近 baseline（大 shape 0.92-0.96x），瓶颈在 host 侧 tiling 选择导致的 num_blocks 过多

**Proposed change**:
在 `tilelang-perf-optimization` 新增"element-wise 算子 host 侧优化决策树"章节（或在 `cann-bench-elementwise-optimization.md` 补强）：
1. **1D shape（M≤2）**：`block_N` cap 从默认 512 提到 8192（UB 预算允许，rows_per_vec=1 时单 buffer 8192×4B=32KB < 192KB）。效果：1D 质数 shape num_blocks 从数千降到数百。
2. **ND shape**：smart-flatten 搜索所有 split point，选 `num_blocks` 最小的 (M, N) 切分。element-wise 算子任何 flatten 不改变结果（只要 contiguous）。
3. **零拷贝前提**：输入 contiguous 时 reshape 只改 metadata（cann-bench 默认 contiguous），不引入 host 拷贝。
4. **判定指标**：`num_blocks = m_num * n_num` 是 compute-bound element-wise op 的 kernel 时间可靠代理（mish case 13: num_blocks -73.1% → kernel -69.2%）。

## Entry e3
- **target_skill**: tilelang-api-best-practices
- **target_artifact**: skill
- **target_section**: api-compute.md T.tile.exp/ln 条目
- **type**: missing_constraint
- **severity**: high
- **status**: applied

**Observation**:
mish 官方测评 3 个 float32 case 精度失败（case 5/11/20，MARE≈0.908），根因疑似 `T.tile.exp` 在 float32 输入下的内部精度问题。同一 kernel 的 fp16/bf16 路径因 cast 到 fp32 中间计算反而精度好（MERE 全 0），但 float32 路径直接用 fp32 buffer 调 `T.tile.exp` 却精度差。这与性能灾难版 attempt 1 踩的坑是同一个问题——`T.tile.exp/ln` 内部可能以 fp16 计算。

**Evidence**:
- 官方测评 `custom/mish/perf_tuning/cannbench_official_iter3.json`：
  - case 5 [8192,8192] fp32 value_range [-100,100]: MERE=0.0152, MARE=0.908（threshold=1.22e-4）❌
  - case 11 [3,7,13,4001] fp32 [-88,88]: MERE=0.0173, MARE=0.908 ❌
  - case 20 [2,3,17,1024,101] fp32 [-20,40]: MERE=0.0449, MARE=0.908 ❌
  - 3 case 共同特征：MARE≈0.908，`small_value_error_count` 占比高
- 同 kernel fp16/bf16 路径（因 cast 到 fp32 中间计算）：MERE 全 0 ✓
- mish kernel `custom/mish/mish.py` L91 `T.tile.exp(t0_ub, t0_ub)` 在 fp32 buffer 上调用
- 对照：性能灾难版 attempt 1 用 `T.tile.exp` 实现 fp32 中间计算，L1 大值域 case 全失败（MARE≈0.9），attempt 2 改用 `T.Parallel + T.exp/T.log` 符号 API 后通过

**Proposed change**:
在 `tilelang-api-best-practices/references/api-compute.md` T.tile.exp/ln 条目下新增警示框："**⚠️ 内部精度限制（待验证）**：`T.tile.exp` / `T.tile.ln` 的内部计算精度行为在 float32 输入 + 大值域（|x|>16）场景下可能不达标（MARE≈0.9）。已知现象：fp16/bf16 路径因 cast 到 fp32 中间计算反而精度好，float32 路径直接用 fp32 buffer 调 T.tile.exp 却精度差。建议：① 用最小 reproducer（单元素 buffer）验证 API 在目标 dtype 下的精度行为；② 若精度不达标，改用 `T.Parallel + T.exp/T.log` 符号 API（preserves buffer dtype，生成 vectorized AscendC::Exp/Ln）；③ `T.tile.sigmoid` 的精度行为可能不同于 exp/ln（mish 用 `2*sigmoid(2s)-1` 实现 tanh 在 fp32 下未触发精度问题，待验证）。参考案例：`custom/mish/mish.py` L91 + 官方 cann-bench case 5/11/20 失败。"

## Entry e4
- **target_skill**: tilelang-perf-optimization
- **target_artifact**: skill
- **target_section**: performance-antipatterns.md Fixed Core 反模式
- **type**: missing_constraint
- **severity**: medium
- **status**: pending

**Observation**:
mish iter4 证伪了"Fixed Core 减少 host 开销"的假设——对 mish 小 shape 反而退化 AVG +15.8% time。skill 的 `performance-antipatterns.md` 已有 Fixed Core 适用边界，但没明确"重计算算子（单 tile 计算步数多）是 Fixed Core 的反模式"。

**Evidence**:
- `custom/mish/perf_tuning/optimization_log.md` Iteration 4：Fixed Core dispatch（num_blocks<100 用 Fixed Core）
- 小 shape 退化数据：case 8 +28.9% time, case 10 +27.2% time, case 15 +21.0% time, case 6 +8.3% time, case 7 +6.2% time
- 根因分析（optimization_log.md L396-415）：① host 开销是 tilelang runtime（Python→C++→ACL launch chain ~12-25us），不是 NPU thread-block 数；② T.serial 循环开销对 mish 12 步计算比例更大；③ bounds guard 分支浪费核周期
- 对照：sigmoid（1 步计算）Fixed Core 也不适用（iter1 已回滚），但 mish（12 步）退化更严重

**Proposed change**:
在 `performance-antipatterns.md` Fixed Core 反模式章节补充判定规则："**Fixed Core 对重计算算子是反模式**。判定标准：单 tile 计算步数 > 4 时，Fixed Core（`launch_cores=min(block_num,24)` + `T.serial`）大概率退化。根因：① host 开销是 tilelang runtime launch chain（~12-25us），与 NPU thread-block 数无关；② T.serial 循环开销 + bounds guard 分支对重计算 per tile 比例更大。参考案例：mish（12 步）Fixed Core 小 shape AVG +15.8% time 退化（`custom/mish/perf_tuning/optimization_log.md` Iteration 4）。"

## Entry e5
- **target_skill**: tilelang-perf-optimization
- **target_artifact**: skill
- **target_section**: optimization-guide.md MEMORY_PLANNING 章节
- **type**: missing_constraint
- **severity**: medium
- **status**: pending

**Observation**:
mish iter5 尝试手写 in-place（`T.tile.mul(a_ub, a_ub, t0_ub)` dst=src0）消除 b_ub buffer，结果性能无变化（-0.4% 噪声）。根因是 `MEMORY_PLANNING=True` 已自动 alias 死 buffer——b_ub 在 a_ub 死亡时诞生，编译器自动复用同一内存。skill 的 `optimization-guide.md` 提到 MEMORY_PLANNING 会复用 buffer，但没明确"手写 in-place 在 MEMORY_PLANNING=True 下是冗余的"。

**Evidence**:
- `custom/mish/perf_tuning/optimization_log.md` Iteration 5：bf16 cast in-place 优化，-0.4% mean speedup（噪声），回滚
- 根因分析（L493-499）："MEMORY_PLANNING=True already aliases b_ub: b_ub is born at step 12 (final mul) exactly when a_ub dies. The compiler's dead-buffer reuse already maps b_ub to a_ub's memory. Explicit in-place produces the SAME memory layout → identical compiled code."
- mish kernel `custom/mish/mish.py` L100 `T.tile.mul(b_ub, a_ub, t0_ub)`（a_ub 之后不再使用，MEMORY_PLANNING 自动 alias）

**Proposed change**:
在 `optimization-guide.md` MEMORY_PLANNING 章节补充："**手写 in-place 在 MEMORY_PLANNING=True 下是冗余的**。编译器已自动 alias 死 buffer（dst=src0 的 in-place `T.tile.mul(a_ub, a_ub, t0_ub)` 与 `T.tile.mul(b_ub, a_ub, t0_ub)` + MEMORY_PLANNING aliasing 产生相同编译结果）。只有关闭 MEMORY_PLANNING 时手写 in-place 才有意义。判定：若 buffer 在某步后不再使用，无需手写 in-place，让编译器自动复用。参考案例：mish iter5 手写 in-place 无性能变化（`custom/mish/perf_tuning/optimization_log.md` Iteration 5）。"

## Entry e6
- **target_skill**: tilelang-op-develop
- **target_artifact**: skill
- **target_section**: coding-conventions.md 或 troubleshooting
- **target_section**: T.tile.sub 不支持 scalar src1 的绕过 pattern
- **type**: missing_api_doc
- **severity**: medium
- **status**: pending

**Observation**:
`T.tile.sub(dst, src0, src1)` 不支持 scalar PrimExpr 作 src1（需要 `1 - x` 时不能直接传 1.0）。mish 用 `T.tile.fill(one_ub, 1.0)` 预填常量 buffer 绕过，这个 pattern 在 skill 里没有记录。

**Evidence**:
- mish kernel `custom/mish/mish.py` L102 `one_ub = T.alloc_shared(...)` + L117 `T.tile.fill(one_ub, 1.0)` + L128 `T.tile.sub(t0_ub, t0_ub, one_ub)`（实现 `tanh = 2*sigmoid - 1` 的 `-1`）
- mish.py L22 注释："T.tile.sub(dst, src0, src1) does NOT accept scalar PrimExpr for src1; use one_ub buffer (pre-filled with 1.0 via T.tile.fill) instead of scalar 1.0."
- 对照：`T.tile.add/mul/max` 接受 scalar PrimExpr 直接（mish L121 `T.tile.add(t0_ub, t0_ub, one_ub)` 也可写 `T.tile.add(t0_ub, t0_ub, 1.0)`）

**Proposed change**:
在 `tilelang-op-develop/references/coding-conventions.md` 或 `tilelang-api-best-practices/references/troubleshooting.md` 新增条目："**`T.tile.sub` 不支持 scalar src1 的绕过 pattern**。`T.tile.sub(dst, src0, src1)` 的 src1 必须是 buffer，不能是 scalar PrimExpr（与 `T.tile.add/mul/max` 不同）。需要 `1 - x` 时：① 用 `T.tile.fill(one_ub, 1.0)` 预填常量 buffer；② `T.tile.sub(dst, one_ub, x_ub)`。参考案例：`custom/mish/mish.py` L102/L117/L128 实现 `tanh = 2*sigmoid(2s) - 1` 的 `-1` 减法。"

- **target_artifact**: skill
- **target_section**: bench 脚本覆盖一致性
- **type**: missing_constraint
- **severity**: medium

**Observation**:
mish perf-tuner 的本地 bench 一开始只覆盖 9 个 shape（3 dtype × S/M/L + 非对齐 + 质数），但 cann-bench 官方测评用全 20 case。本地 bench 与官方偏差大（本地 0.449 vs 官方 0.7168，差 +59.6%），且本地 bench 无法提前发现 3 个 float32 case 的精度失败（case 5/11/20 在本地 bench 用 [-1,1] value_range，未覆盖官方的大值域）。

**Evidence**:
- `custom/mish/perf_tuning/perf_report.md` §3.1 本地 bench 9 shape，mean speedup 0.449
- `custom/mish/perf_tuning/cannbench_official_iter3.json` 官方 20 case，mean speedup 0.7168
- 偏差 +59.6%（官方高出本地 59.6%），与 skill 文档记录的 mish 偏差 +58% 一致
- 3 个 float32 case 失败（case 5/11/20）在本地 bench 未覆盖（本地用 [-1,1]，官方用 [-100,100]/[-88,88]/[-20,40]）

**Proposed change**:
在 `tilelang-perf-optimization` SKILL.md bench 脚本章节新增约束："本地 bench **必须覆盖 cann-bench cases.yaml 全 20 case**（与官方测评一致），包括：① 全部 dtype（float16/float32/bfloat16）；② 全部 value_range（含大值域 case 5/11/20 的 [-100,100]/[-88,88]/[-20,40]）；③ 全部 shape（含 1D 质数 case 12、5D case 13/20）。特殊值 case（inf/nan/zero）可标注为非精度可比但必须跑性能。若某 case 本地无法跑（如 OOM），必须在 perf_log 中记录原因并估算其对 mean speedup 的影响。禁止以'comparable'为由排除任何 case。"
