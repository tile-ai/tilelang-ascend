# Skill Feedback - mish

## Entry e1
- **target_skill**: tilelang-perf-optimization
- **target_artifact**: skill
- **target_section**: §2.6 指令向量化 / 性能反模式
- **type**: missing_constraint
- **severity**: high
- **status**: applied

**Observation**:
`tilelang-perf-optimization` skill 没有明确警示：element-wise 算子若用 `T.if_then_else` 条件分支，会因无法被 `ascend_lower_parallel` pass 向量化而降级为串行循环（每个 tile 64×128=8192 次标量迭代），导致性能灾难性下降。mish 算子用 `T.if_then_else` 解决大负值域精度问题后，本地 bench mean speedup 仅 0.0112（比 baseline 慢 89 倍），根本原因就是串行循环。

**Evidence**:
- mish kernel `custom/mish/mish.py` L152-158 用 `T.if_then_else` 做 x < -8.0 条件分支
- perf-tuner 通过 `get_kernel_source()` 检查生成代码，发现 AUTO_SYNC=True 时串行循环内被插入 8192 个 per-element `PipeBarrier<PIPE_ALL>()`，占总 kernel 时间 ~30%
- 即使优化为 AUTO_SYNC=False 消除 barrier，串行循环本身仍是性能杀手：本地 bench case 1 (1024×1024 fp16) kernel 1.88ms，baseline `torch.nn.functional.mish` 在 NPU 上是高度优化的 fused kernel
- 性能目标 0.6，实际本地 0.0159，差 38 倍

**Proposed change**:
在 `tilelang-perf-optimization` SKILL.md §2.6 指令向量化章节新增硬约束："element-wise 算子**禁止用 T.if_then_else 做逐元素条件分支**——会降级为串行循环导致性能灾难。需要条件分支时，优先用数学等价变换（如 log-sum-exp trick）或分段多项式逼近消除分支；若必须用条件分支，需评估是否可接受串行循环代价，或探索 T.tile.compare/select 替代（注意 128 元素 mask 反转 bug）。"

## Entry e3
- **target_skill**: tilelang-api-best-practices
- **target_artifact**: skill
- **target_section**: api-compute.md §4.2 T.tile.exp/ln
- **type**: missing_constraint
- **severity**: high
- **status**: applied

**Observation**:
`T.tile.exp` / `T.tile.ln` / `T.tile.reciprocal` 内部以 **fp16** 计算无论 buffer dtype 是什么，导致 fp32 中间计算方案失效。这个关键限制在 api-compute.md 中没有明确标注，mish Stage 2 attempt 1 用 `T.tile.exp/ln` 实现 fp32 中间计算导致 L1 大值域 case 全失败（MARE≈0.9），attempt 2 才发现必须改用 `T.Parallel + T.exp/T.log` 符号 API。

**Evidence**:
- mish Stage 2 attempt 1 用 `T.tile.exp/ln` 实现 fp32 中间计算，L1 6 个大值域 case 失败（case 5/9/10/11/17/20，MARE≈0.9）
- attempt 2 改用 `T.Parallel + T.exp/T.log` 符号 API 后通过，原因：符号 API preserves buffer dtype，生成 vectorized `AscendC::Exp/Ln`
- 参考 `custom/sigmoid/sigmoid.py` 注释也提到此限制
- `testing/python/language/parallel/test_tilelang_ascend_language_parallel.py` 验证了 T.Parallel + T.exp/T.log 的 lowering 模式

**Proposed change**:
在 `tilelang-api-best-practices/references/api-compute.md` §4.2 T.tile.exp/ln 条目下新增警示框："**⚠️ fp16 内部计算限制**：`T.tile.exp` / `T.tile.ln` / `T.tile.reciprocal` 内部以 fp16 计算无论 buffer dtype。需要 fp32 精度时必须用 `T.Parallel + T.exp/T.log` 符号 API（preserves buffer dtype，生成 vectorized AscendC::Exp/Ln）。参考 `testing/python/language/parallel/` 验证模式。"

**Observation**:

**Proposed change**:

## Entry e5
- **target_skill**: tilelang-api-best-practices
- **target_artifact**: troubleshooting
- **target_section**: T.tile.compare + T.tile.select mask 反转 bug
- **type**: known_bug_avoidance
- **severity**: high
- **status**: pending

**Observation**:
`T.tile.compare` + `T.tile.select` 在 128 整数倍 buffer 上有 mask 后 64 位反转 bug，troubleshooting.md 已记录。但 mish 算子开发中仍反复考虑使用此 API（buffer 是 64×128=8192 = 128 的整数倍），直到 attempt 2 才确认不可用。需要强化规避指引：给出**可用的替代方案**。

**Evidence**:
- mish DESIGN.md §1.4 明确禁止 T.tile.compare + T.tile.select，引用 troubleshooting.md §1
- mish Stage 2 attempt 2 debug_log 记录："T.tile.compare+select: 128 整数倍 buffer mask 反转 bug，8192 是 128 倍数，不可用"
- perf-tuner Stage 3 仍考虑用 compare/select 替代 T.if_then_else 消除串行循环，再次踩坑
- 当前可用替代：T.if_then_else（但导致串行循环）、数学等价变换（消除分支）

**Proposed change**:
在 `tilelang-api-best-practices/references/troubleshooting.md` T.tile.compare/select bug 条目下新增"替代方案"小节："规避此 bug 的可用方案：① `T.if_then_else`（注意会降级为串行循环，性能代价大）；② 数学等价变换消除条件分支（首选，如 log-sum-exp trick）；③ 分段多项式逼近（如 softplus(x) ≈ max(x,0) 当 |x|>threshold）。**禁止在 128 整数倍 buffer 上用 compare/select**，必须用以上替代。"
