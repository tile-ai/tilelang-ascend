# 方案与验证

## 方案准入

每个方案进入实施前必须满足：

1. 至少一个本轮瓶颈证据支持其假设。
2. 涉及的 TileLang API 和调用结构能在当前仓库或实际导入的 TileLang 源码中定位。
3. 若复用名为 `tilelang-performance-best-practices` 的 Skill 中的 bundled reference，记录 Skill 名称、内部 Python 文件相对路径和成熟度；若方案仅依据当前仓库或实际 TileLang 源码，则记录对应源码路径及直接验证证据，不要求先登记到模板状态表。
4. 明确覆盖 case、互斥分支、精度风险和回退条件。
5. 给出可复现的 lowering、精度和性能验证方法。

不满足第 2 项时标为 `DESIGN_ONLY`，不能交给直接实施阶段。复用 bundled reference 却不满足第 3 项时，不得把该 reference 作为直接复用模板；但若当前仓库或实际 TileLang 源码另有完整的 API、lowering、精度和适用范围证据，可依据这些直接证据独立准入。

## 报告模板

### 1. 环境与基线

- 当前仓库路径/commit、实际导入的 TileLang 路径/版本、CANN 与实际后端版本、设备。
- 编译、测试和 profiling 命令及关键环境变量。
- 全部 case 的 dispatch、精度状态、latency 和瓶颈证据。

### 2. 已准入方案概览

| 优先级 | 方案 | 核心假设 | 状态 | 覆盖 case | 预期观察 |
|---:|---|---|---|---|---|

已准入方案最多三个，状态仅使用：

- `IMPLEMENTABLE`：API、参考实现和 lowering 依据齐全。
- `EXPERIMENT`：可执行但收益或适用范围尚需隔离实验。

`DESIGN_ONLY` 不属于已准入方案，单列到“未准入候选”，不占三个方案名额，也不交给实现阶段。

### 3. 每个方案

- 瓶颈证据与可证伪假设。
- 修改的 TileLang 文件、函数、dispatch 分支和参数。
- 当前值 → 候选值及 Tiling/buffer 计算。
- 参考 Python 路径、模板成熟度和关键 TileLang 结构。
- 逐 case 覆盖表。
- 编译、精度、性能验收和回退条件。

最多输出三个已准入方案。若几个优化点必须同时出现才能构成一个合法数据流，可合并为一个方案并解释依赖；否则优先分开验证，便于归因。

### 4. 未准入候选（可选）

| 候选 | 状态 | 未准入原因 | 缺失证据 | 后续验证 |
|---|---|---|---|---|

这里只列 `DESIGN_ONLY`。它用于保留可能有价值但当前无法由 TileLang A2/A3 直接实施的方向，不参与方案排序、实施或性能比较。

### 5. 全量 case 覆盖

| Case | 基线组 | dispatch | 方案 | 预期变化 | 验证状态 |
|---|---|---|---|---|---|

所有 case 必须出现。没有适用方案的 case 标记“暂不修改”并说明原因。

## 验证顺序

按目标仓库测试规范执行：

1. 当前后端 lowering/编译：先运行最小相关 case，保留完整错误信息。
2. 精度：使用仓库既有 reference 和阈值，覆盖方案全部分支、边界和尾块。
3. 性能：基线与候选保持设备、输入、warmup、repeat、并发和计时层级一致；逐 case 记录 kernel latency。
4. 扩大回归：最小集合通过后再运行当前仓库要求的定向精度测试、相关完整测试套和合入前项目要求的扩展测试。

独立 pytest 测试的常用入口（执行者先按工程要求加载环境）：

```bash
pytest <test_file> -x
```

若目标工作流规定了其他命令，以目标仓库当前规范为准。

## 性能结论

逐 case 加速比为 `baseline_latency / candidate_latency`。汇总值必须说明算法（例如几何平均），同时单列最差退化 case。只有全部精度门禁通过且同口径实测完成后，才能称为性能优化；否则只报告实验结果或设计建议。

## 采纳证据与阶段职责

逐 case 加速比为 `baseline_latency / candidate_latency`；汇总时注明算法并单列最差退化和噪声。候选正确性失败不能参与性能评选。没有同口径实测，只能称为设计或实验结果。

是否采纳、如何回滚、容许多少轮及最终归档由调用方规定；本技能不创建另一套迭代状态。报告写入调用方指定位置。后续实施者应接收报告、源码版本、case 清单、测试契约和证据路径，避免重新猜测条件。

## A2/A3 实施交接补充

本技能设计以上验证顺序，实际运行由实施阶段和调用方完成。测试入口从当前工程获取，可为内嵌测试单文件或独立 pytest；不假设固定 `--level all` 参数。保持已有编程模式、reference 和容差。流水方案还需明确循环内 MTE3、跨迭代累加器、同步方式、版本化对象及首轮/尾轮所有权；扩大调用域先完成对应专题的 kernel 复用审计。
